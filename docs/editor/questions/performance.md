# Kēne Performance 体验问答文档

## 1. 文档用途

这份文档用于从零定义 Kēne Editor 中 Performance 工具的产品角色。讨论重点不是“显示更多数字”，
而是让作者或开发者能够回答具体问题，同时保证每个指标都来自真实测量、具有明确口径，并且不会因
VSync、采样开销或跨进程延迟产生误导。

## 2. 给 Chat 的工作方式

1. 一次只问一个问题。
2. 每题说明用户最终能做出什么判断，而不只是列出可能的指标。
3. 把“当前已有数据”“可以低成本增加的数据”“需要引擎或平台测量的数据”分开。
4. 不允许用估算值、动画值或传输吞吐量冒充 CPU/GPU 帧耗时。
5. 性能优化方向必须从可重复热点开始；工具界面本身不是优化结论。
6. 用户回答后记录目标用户、指标定义、采样条件、开销和验收设备。
7. 问答阶段不开始实现，也不默认需要第三方 profiler 或新依赖。

可直接使用的开场提示：

> 请基于本文主持 Kēne Performance 工具问答。先解释当前面板实际测量了什么、没有测量什么，然后一次只问一个产品问题。所有指标必须给出来源、单位、采样窗口和局限，不要为了丰富界面发明数据。

## 3. 当前 Preview 与 Performance 背景

Kēne Editor 与 Engine 是两个可独立运行的进程。Editor 启动一个预编译 Engine authoring child，
通过有界二进制协议控制 Preview。

Preview 当前使用最新帧优先的共享内存三缓冲：

- Engine 在隐藏的 1920×1080 目标中保持正常三相机合成；
- 同一时间最多一个 GPU readback 在途；
- Editor 只传输并上传最新完成帧；
- 旧帧可以被覆盖，而不是排队积累输入延迟；
- Preview 隐藏、窗口不活跃或显式停止时有独立生命周期和降工作策略；
- Preview 的目标是交互可靠，不是成为完整游戏性能分析器。

## 4. 当前 Performance 面板实际显示什么

当前 Performance 是可关闭的 singleton 工具视图，只显示 Preview transport 的真实计数：

- Published frames：Engine 已发布到共享帧槽的累计帧数；
- Overwritten frames：来不及被 Editor 消费而被新帧覆盖的累计数量；
- Samples：面板当前保留的采样数量；
- 以 500 ms 为间隔的发布帧增量柱状图。

面板明确标注这些数据不是 CPU 或 GPU frame time。

当前没有：

- CPU 主线程或系统级占用；
- GPU 时间、提交时间或 readback 时间线；
- Editor upload/composite 耗时；
- 端到端输入延迟；
- 内存、显存、音频缓冲或媒体解码压力；
- 场景、Action、资源加载与卡顿事件的关联；
- 录制、导出、基线对比或自动结论。

## 5. 已有性能证据原则

- 性能改变需要同条件、可重复的前后测量。
- 60 Hz VSync 封顶的结果只能证明没有明显回归，不能证明 GPU 吞吐上限。
- 一次尖峰不能直接归因于某个系统；需要定位到时间线并重复采样。
- 不同平台、GPU、DPI、窗口状态和缓存状态必须随报告记录。
- 不活跃功能应尽量静态专门化；关闭某功能时不应继续支付明显成本。
- UI 只能展示已经测得的事实，不能把推断包装成绿色健康状态。

### 已确认的产品与实现约束

- 性能优先，但只为已证明的工作负载增加机制；不预建通用遥测平台、插件层或多套采样管线。
- Editor 空闲时不进行文件全量扫描、Manifest 全量解析、媒体探测、不可见缩略图解码或持续无意义重绘。
- 大列表只处理可见项目；文件与 Asset 索引按变化增量失效；缓存必须有界且不是工程事实来源。
- 媒体探测、缩略图解码和确实耗时的文件工作不得阻塞 UI 线程。
- 用户操作的状态反馈必须立即出现；短动画只表现已经发生的变化，不能延迟选择、点击或拖放结果。
- 视觉延续当前暗色、短圆角和克制强调色；能用现有图标表达的动作不增加文字按钮。
- 提示文字使用完成判断所需的最少内容；批量工作只给一条汇总，不为每个文件刷 Toast。
- 任何性能优化都需要同条件前后测量；实现不同但最终交互结果和证据口径必须一致。

## 6. 待讨论问题

### Q1. Performance 面板首先服务谁？

- A：普通 VN 作者，只需判断 Preview 是否健康以及哪里可能阻塞。
- B：Kēne 引擎开发者，需要底层时间线与调试指标。
- C：同一工具提供默认 Author 模式和显式 Developer 模式。

**建议方向：C。** 默认界面保持少而可信；Developer 模式再显示有口径的细节，避免普通作者面对无法行动的数字。

### Q2. 默认面板要回答什么问题？

- A：只回答“Preview 是否持续出帧”。
- B：回答“画面、资源、媒体或传输中的哪一段可能导致体验问题”。
- C：给出一个综合性能分数。

**建议方向：B，但分阶段实现。** C 容易把不同硬件、场景和指标压成没有解释力的分数。

### Q3. 当前 transport 数据如何升级？

- A：保留累计 Published/Overwritten 数量。
- B：增加窗口化 publish rate、overwrite rate、消费间隔和 Preview 状态事件。
- C：把柱状图标成 FPS。

**建议方向：B。** 只有在口径确实等于呈现帧率时才能使用 FPS 名称；发布速率不是最终显示帧率。

### Q4. 是否显示 CPU/GPU 时间？

- A：不显示，保持 transport-only。
- B：只有 Engine/Editor 提供真实时间戳或平台查询结果时显示，并标明测量区间。
- C：根据发布帧间隔估算 CPU/GPU 时间。

**建议方向：B。** C 明确禁止。需要分别定义 simulation、render、GPU、readback、IPC、upload 与 composite 的边界。

### Q5. 时间线以什么为中心？

- A：连续折线图。
- B：事件时间线，卡顿、Preview 生命周期、资源加载和媒体事件与采样叠加。
- C：只显示当前瞬时数字。

**建议方向：B，辅以少量趋势图。** 作者需要知道“什么时候、发生了什么”，而不是只看数字波动。

### Q6. 如何定义异常？

- A：统一使用固定红黄阈值。
- B：根据目标帧率、Preview 状态、平台和测量类型设置可解释阈值。
- C：与最近一次采样自动比较，任何变化都报警。

**建议方向：B。** 阈值必须对应用户可感知后果；暂停、隐藏和停止状态不能被误报为掉帧。

### Q7. 是否需要场景和源码关联？

- A：不关联，只显示全局指标。
- B：记录当前 scene/source cursor 和主要 runtime event，允许从时间线回到源码。
- C：为每个 Action 自动生成完整 profiling 记录。

**建议方向：B。** 关联身份必须来自现有稳定 source identity，不能通过显示文本反向猜测。

### Q8. 资源与媒体需要哪些信息？

- A：仅显示最近加载的文件名。
- B：显示有界的加载/解码事件、资源类型、耗时、失败和是否来自缓存。
- C：持续显示所有资源的完整内存对象图。

**建议方向：B。** 内存或缓存数字只有在定义清楚所有者、生命周期和单位后才可以展示。

### Q9. 性能采样默认是否开启？

- A：所有详细采样始终开启。
- B：保留低成本健康计数；高成本时间线由用户明确开始并有自动上限。
- C：只有命令行模式可以采样。

**建议方向：B。** 面板关闭、Preview 停止或窗口隐藏时，不应因为监控本身保持高频工作。

### Q10. 如何控制采样体积？

- A：无限保留当前会话。
- B：使用固定时间窗或环形缓冲，用户可以显式冻结一次捕获。
- C：每次自动写入磁盘。

**建议方向：B。** 默认不产生长期磁盘日志；冻结后才允许检查或导出。

### Q11. 是否需要导出报告？

- A：不导出，只在 UI 中查看。
- B：导出一个去除敏感路径、包含指标定义和环境元数据的有界报告。
- C：直接上传到在线服务。

**建议方向：B。** 自动上传不在当前范围；绝对路径、项目内容和发布身份不能无意泄漏。

### Q12. 如何进行前后对比？

- A：用户肉眼比较两张图。
- B：导入或选择两个同口径捕获，显示硬件、commit、场景和采样条件差异。
- C：自动把任何两个会话计算为百分比提升。

**建议方向：B。** 条件不一致时应拒绝给出确定优化结论，或把差异明确标为不可比较。

### Q13. Author 模式应该显示哪些摘要？

- A：FPS、CPU、GPU、内存四张大卡片。
- B：Preview 状态、帧传输健康、最近一次可行动事件，以及进入详细捕获的入口。
- C：单一绿色/黄色/红色状态灯。

**建议方向：B。** 不用大卡片填满空间，也不把复杂系统压成缺乏证据的交通灯。

### Q14. Developer 模式的层级如何组织？

- A：按指标名称排列。
- B：按端到端管线排列：simulation → render/GPU → readback → transport → Editor upload/composite。
- C：按线程名称排列。

**建议方向：B。** 它最接近定位体验问题的因果链；线程与平台细节可以作为展开信息。

### Q15. 什么情况下允许提出优化建议？

- A：任何红色指标都自动生成建议。
- B：只有检测到可重复、口径明确的异常时，面板提供证据链接和下一步测量建议。
- C：面板永远不显示任何解释。

**建议方向：B。** 工具可以指导验证，但不能从一次采样直接声称某个模块需要重写。

## 7. 可能涉及的跨层接口

问答若选择扩展指标，可能涉及：

- Editor：采样控制、时间线、过滤、冻结和报告 UI；
- Authoring protocol：有界、版本化的性能事件或快照；
- Runtime：simulation、生命周期与 source identity 事件；
- Render：可靠 GPU 查询或提交边界；
- Scene/Media：资源加载、解码和播放缓冲事件；
- Frame transport：发布、覆盖、消费与代际统计；
- Storage：仅在用户明确保存捕获时写入有界报告。

任何新增事件都必须说明是否在 release、authoring-host 或仅开发构建中启用，不能让性能观测显著改变被观测对象。

## 8. 问答结束后的交付结构

最终方案至少应包含：

- Author 与 Developer 两类用户分别要回答的问题；
- 指标表：名称、来源、单位、采样窗口、成本、局限和可用平台；
- 默认低成本计数与显式详细捕获的边界；
- 时间线事件、源码/场景关联和导航流程；
- 暂停、隐藏、停止、VSync 封顶和缓存预热等特殊状态的解释；
- 捕获、冻结、比较、导出和隐私规则；
- 跨进程协议与各模块所有权；
- 至少一套真实低端设备和一套现代设备的验收计划。

## 9. 明确禁止的捷径

- 不把 publish rate、sample count 或动画柱高标成 CPU/GPU frame time。
- 不根据一次尖峰自动归因。
- 不用综合分数替代可解释指标。
- 不让详细采样无限增长或在面板关闭后继续高频运行。
- 不用 VSync 封顶结果证明渲染吞吐提升。
- 不在报告中默认包含绝对路径、源码、密钥、发布身份或其他敏感信息。
- 不为了 Performance UI 先引入通用遥测平台、网络服务或新依赖。
